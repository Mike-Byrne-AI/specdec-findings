exact verifier

Exact verifier: the speculative-decoding accept/reject step in numpy

sideband · folder

6 files, 29146 bytes; MIT licence.

Contents: spec_step; run_block; residual_distribution; analytic_acceptance; StepOutcome; BlockOutcome; RunMetrics.

Tests of this copy: 24 passed

How to use this tool

A speculative decoder lets a small draft model guess the next tokens and a large model check them. This is the checking rule: it keeps or replaces each guess so that the text that comes out follows the large model's own probabilities exactly, whatever the draft guessed. The tests prove that by counting through every outcome.

  1. Copy the command under Get this folder, run it, then run the tests to see the rule hold.
  2. In your code, import spec_step from sideband.specdec. Give it a numpy random generator, then the large model's probabilities, then the draft's, for one position over the same vocabulary.
  3. It returns a StepOutcome: the token the draft proposed, whether it was kept, and the token that came out.
  4. For a block of several guesses use run_block, with one more large model distribution than draft distributions; the extra one gives a bonus token when every guess is kept.
  5. If you write a faster version, make these tests pass against it before you trust it.

A numpy implementation of the exact speculative-decoding accept/reject step (Leviathan et al. 2023) with tests that check by enumeration that the emitted token follows the target distribution for any draft distribution; for researchers building or changing speculative decoders.

In the record

In the record this file is the single implementation of accept, reject and residual (DECISIONS.md D-3: the real-model adapter converts logits to numpy and calls spec_step, and anyone re-implementing the verifier for speed must first make these numpy tests pass against their implementation). Its docstring states the property the tests check by enumeration: for any draft distribution, steered or not, the emitted token is distributed exactly as the target distribution, so steering can only change speed, never output quality.

Use

Good to know

  • Per-step acceptance is analytically 1 - TV(p, q), and that identity is tested too.
  • The docstring names the record's real-model adapter (sideband.real.hf_specdec, not copied) and the test file, which is copied here.

cluster bootstrap stats

Cluster bootstrap: confidence intervals for prompt-clustered evaluations

sideband · folder

7 files, 35410 bytes; MIT licence.

Contents: clopper_pearson; cluster_bootstrap_ci; paired_cluster_delta_ci; paired_ratio_delta_ci; paired_ratio_delta_of_deltas_ci; e6_gate.pair; e6_gate.evaluate.

Tests of this copy: 38 passed, 2 skipped

How to use this tool

When two methods are scored on the same prompts, results from one prompt tend to move together, so treating every result as independent makes the uncertainty look smaller than it is. These functions give confidence intervals that resample whole prompts, and when comparing two methods they resample both with the same draw, so the difference is a fair paired one.

  1. Copy the command under Get this folder, run it, then run the tests.
  2. For each prompt, count the successes of method A, the successes of method B and the number of trials, with the prompts in the same order in all three arrays.
  3. Call paired_cluster_delta_ci with those three arrays. It returns the difference between the two success rates and the low and high ends of its 95% interval.
  4. For one method alone use cluster_bootstrap_ci. With nothing to group by, clopper_pearson gives the exact interval for k successes in n trials.
  5. The same seed always gives the same interval, so fix the seed before you look at results.

Numpy-only confidence intervals for clustered evaluation data: an exact Clopper-Pearson interval, a prompt-cluster percentile bootstrap, and paired delta and paired ratio-delta bootstraps that apply one resampling draw to both arms; for researchers comparing two methods on the same prompts.

In the record

stats.py is the estimator the record's root README recomputes a finding with in its worked example (paired_ratio_delta_ci over a committed state file), and the one its conversion gate, tools/e6_gate.py, imports; several record instruments carry bootstraps of their own beside it. Its docstring reports the pair of estimators together on purpose: the exact binomial interval assumes independent trials, which positions within a prompt are not, and the percentile bootstrap under-covers at small cluster counts (its docstring gives the measured coverage at 10, 30 and 60 clusters for a nominal 0.95), so neither end is conservative and both are reported.

Use

  • stats.py needs only the Array alias from dists.py; copy both, or inline the alias.
  • tools/e6_gate.py is a worked example of the paired-delta gate, not an API: its population table, results path and bar constants are the record's own runs.
  • Run python -m pytest from this folder. Two legs of test_e6_gate skip here because they read the record's committed verdict summaries.

Good to know

  • The Clopper-Pearson reference values in the tests were generated once from scipy.stats.beta and committed; scipy is not a dependency.
  • The bootstrap is deterministic given its seed; the paired forms apply one resampling draw to both arms, which is what makes the delta a paired delta.

rank census

Rank census: does a model's token ranking reproduce across environments?

amber · folder

4 files, 17769 bytes; MIT licence.

Contents: rank_census; rank_census_topk; calibrate_tau; calibrate_tau_topk; RankCensus; stable_topk; top2_gap; canonical_topk; aligned_delta.

Tests of this copy: 10 passed

How to use this tool

The same model on two machines, or at two batch sizes, can rank its candidate next tokens a little differently. This tool takes the scores from both runs at the same positions and reports how often the top token, the top few tokens and their order change, and how close the top two scores were where the top token changed.

  1. Copy the command under Get this folder, run it, then run the tests.
  2. Save the model's scores (logits) at the same positions from each run as a numpy array with one row per position and one column per vocabulary entry.
  3. Call rank_census with the reference run first and the other run second.
  4. Read the RankCensus it returns: how often the top token flipped, how often the top 1, 8 and 64 changed as a set and in order (the ks argument sets those sizes), and the smallest, median and largest gap between the top two scores where the top token flipped.
  5. Its only dependency is numpy, so you can copy rankcensus.py on its own.

A numpy instrument that compares two logit dumps of the same positions (for example two devices or batch sizes) and reports top-1, top-k set and top-k order flip rates, the top-2 gap at each flip, a calibrated tolerance and flip burstiness; for researchers checking whether a model's token ranking reproduces across environments.

In the record

In amber this is the instrument for its rank-stability question: amber's determinism contract is that the draft's token ordering reproduces at decode time, not its logits bitwise, and this module measures how far two logit dumps of the same teacher-forced positions disagree in exactly that quantity. Its docstring explains why every top-1 flip carries the reference top-2 gap (a flip at a hairline gap is floating-point noise, a flip at a wide gap is a bug) and why the tolerance is calibrated from a benign perturbation rather than picked.

Use

  • One file with no internal imports: copy src/amber/rankcensus.py alone, or the folder.
  • Run python -m pytest from this folder.

Good to know

  • The docstring credits the owner's other research projects by name as the sources of its rules (the calibrated tolerance, the near-tie budget, the drift-census shape); those are provenance notes, not imports, and would be reworded for a standalone card.
  • Order convention is descending value, ascending index on ties, the same as amber's codec, so the instrument and the codec agree on what a rank is.

synthetic testbed

Synthetic testbed: a CPU world for draft-steering experiments

sideband · folder

14 files, 78787 bytes; MIT licence.

Contents: WorldConfig; World; TelemetryDataset; run_simulation; train_sidecar; SimResult; POLICIES; HashSketch; SoftmaxRegression; GatedSteerer; posterior_bias; bucket_bias.

Tests of this copy: 68 passed

How to use this tool

A small made up world that runs on an ordinary CPU: a large model, a draft model and a stream of side information, all generated from a hidden topic that changes now and then. Because the hidden truth is known, you can try an idea for steering the draft, and check the code behind it, before spending time on real models.

  1. Copy the command under Get this folder, run it, then run the tests.
  2. Make a world with World(WorldConfig()); change the fields of WorldConfig, its seed among them, to shape it.
  3. Call run_simulation(world, seed, n_positions, gamma, policy=...) once for each name in POLICIES and compare the SimResult each returns; gamma is the number of draft guesses per check.
  4. The learned policy needs a trained model first, which train_sidecar makes.
  5. Know its limit: here the side information and the large model come from the same hidden topic, so no steering can beat the free baseline in this world. Whether real models allow more is a question it cannot answer.

A numpy synthetic world (a sticky concept chain with target, draft and hashed telemetry) wired to an exact speculative decoder and five policies (vanilla, two oracles, the free-information baseline and a learned sidecar), so steering and analysis code can be checked against known ground truth on CPU; for researchers prototyping draft-steering ideas.

How to use this tool

A check for a research log. Every finding in FINDINGS.md must say under what conditions it was measured (a regime line) and point to evidence files that git tracks (source lines). The check fails when a finding is missing either, or cites a file that does not exist or that git does not track.

  1. Copy the command under Get this folder and run it, then copy lint_findings.py from the new folder's tools folder into a tools folder at the root of your repository. It finds the root from where it sits and reads FINDINGS.md there.
  2. Give each finding a heading that starts ## F-, a line that starts - regime: and one or more lines that start - source: naming files under results/, tests/, docs/ or the other folders listed at the top of the file.
  3. Run python tools/lint_findings.py. It prints FAIL and exits with code 1 when a finding fails; add it to your make lint target and to your CI so it runs every time.
  4. Change the list of evidence folders at the top of the file to fit your layout.
  5. In this folder one of its five tests fails as expected: it reads the record's own FINDINGS.md, which is not copied.

A stdlib-only lint that fails a FINDINGS.md whose entries lack a regime line or a source line pointing at paths git tracks; for research repositories kept by people or coding agents, wired to make lint and CI.

Get this folder

How to use this tool

A helper for the text that reports a result. Instead of typing numbers into a sentence, you pass each one through the tool, which records where it came from; a check then flags any number in the finished text that no result file holds. It also blocks banned phrases and reports mixed line endings.

  1. Copy the command under Get this folder, run it, then run the tests.
  2. In the script that writes your text, load your primary and replication result files with Pair and insert every number through it. Pair expects this record's result layout, so adapt its field names to yours first.
  3. Call Pair.write with a folder and your texts; it saves them beside a numbers.json file listing every number used.
  4. Run python tools/landing_text.py check numbers.json --files your_text.md. Each number it cannot trace is printed as a FINDING and the exit code is 1.
  5. python tools/landing_text.py eol reports the line ending of each file.

A stdlib-only tool for writing the text that lands a result: pairs of generated sentences and the payload fields they quote, a check that no number in the text is unknown to a payload, a banned-phrase assertion, a line-ending normaliser and a CLI; for research repositories whose results are landed by a coding agent.

How to use this tool

Instructions that make Claude Code a second, sceptical reviewer for your experiments. Before you commit a result, it checks the change against a nine item checklist, marks each objection as blocking or advisory, and can recompute the claimed numbers from your saved run files instead of trusting the text.

  1. Copy the command under Get this folder and run it; the folder holds the two instruction files and the licence.
  2. Put sideband-critic.md in your project's .claude/agents/ folder and SKILL.md at .claude/skills/critic/SKILL.md.
  3. Rewrite the nine checklist items for your own work: as copied they refer to this record's decisions and findings.
  4. In Claude Code, type /critic, or ask it to run the critic on a change, a finding or a result file. Ask for recompute mode when you want the numbers checked.
  5. The agent file names a model and the tools it may use; set both for your own setup.

A Claude Code review-agent prompt and a /critic skill that check an experiment change or a finding against a nine-item checklist, tag each objection BLOCKING or ADVISORY, and in recompute mode re-derive the asserted numbers from committed state files; for researchers who run experiments with a coding agent.
