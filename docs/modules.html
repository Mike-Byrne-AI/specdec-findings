sideband · folder

Exact verifier: the speculative-decoding accept/reject step in numpy

A numpy implementation of the exact speculative-decoding accept/reject step (Leviathan et al. 2023) with tests that check by enumeration that the emitted token follows the target distribution for any draft distribution; for researchers building or changing speculative decoders.

Use

  • Copy src/sideband/ into your project, or vendor specdec.py and dists.py together (specdec imports normalize, sample and tv_distance from dists).
  • steering.py is here only because the test file uses its bucket_bias; it is not needed to call spec_step.
  • Run python -m pytest from this folder: pytest.ini points it at the copied tests and this folder's src/.

Good to know

  • Per-step acceptance is analytically 1 - TV(p, q), and that identity is tested too.
  • The docstring names the record's real-model adapter (sideband.real.hf_specdec, not copied) and the test file, which is copied here.

In the record

In the record this file is the single implementation of accept, reject and residual (DECISIONS.md D-3: the real-model adapter converts logits to numpy and calls spec_step, and anyone re-implementing the verifier for speed must first make these numpy tests pass against their implementation). Its docstring states the property the tests check by enumeration: for any draft distribution, steered or not, the emitted token is distributed exactly as the target distribution, so steering can only change speed, never output quality.

sideband · folder

Cluster bootstrap: confidence intervals for prompt-clustered evaluations

Numpy-only confidence intervals for clustered evaluation data: an exact Clopper-Pearson interval, a prompt-cluster percentile bootstrap, and paired delta and paired ratio-delta bootstraps that apply one resampling draw to both arms; for researchers comparing two methods on the same prompts.

Use

  • stats.py needs only the Array alias from dists.py; copy both, or inline the alias.
  • tools/e6_gate.py is a worked example of the paired-delta gate, not an API: its population table, results path and bar constants are the record's own runs.
  • Run python -m pytest from this folder. Two legs of test_e6_gate skip here because they read the record's committed verdict summaries.

Good to know

  • The Clopper-Pearson reference values in the tests were generated once from scipy.stats.beta and committed; scipy is not a dependency.
  • The bootstrap is deterministic given its seed; the paired forms apply one resampling draw to both arms, which is what makes the delta a paired delta.

In the record

stats.py is the estimator the record's root README recomputes a finding with in its worked example (paired_ratio_delta_ci over a committed state file), and the one its conversion gate, tools/e6_gate.py, imports; several record instruments carry bootstraps of their own beside it. Its docstring reports the pair of estimators together on purpose: the exact binomial interval assumes independent trials, which positions within a prompt are not, and the percentile bootstrap under-covers at small cluster counts (its docstring gives the measured coverage at 10, 30 and 60 clusters for a nominal 0.95), so neither end is conservative and both are reported.

amber · folder

Rank census: does a model's token ranking reproduce across environments?

A numpy instrument that compares two logit dumps of the same positions (for example two devices or batch sizes) and reports top-1, top-k set and top-k order flip rates, the top-2 gap at each flip, a calibrated tolerance and flip burstiness; for researchers checking whether a model's token ranking reproduces across environments.

Use

  • One file with no internal imports: copy src/amber/rankcensus.py alone, or the folder.
  • Run python -m pytest from this folder.

Good to know

  • The docstring credits the owner's other research projects by name as the sources of its rules (the calibrated tolerance, the near-tie budget, the drift-census shape); those are provenance notes, not imports, and would be reworded for a standalone card.
  • Order convention is descending value, ascending index on ties, the same as amber's codec, so the instrument and the codec agree on what a rank is.

In the record

In amber this is the instrument for its rank-stability question: amber's determinism contract is that the draft's token ordering reproduces at decode time, not its logits bitwise, and this module measures how far two logit dumps of the same teacher-forced positions disagree in exactly that quantity. Its docstring explains why every top-1 flip carries the reference top-2 gap (a flip at a hairline gap is floating-point noise, a flip at a wide gap is a bug) and why the tolerance is calibrated from a benign perturbation rather than picked.

sideband · folder

Synthetic testbed: a CPU world for draft-steering experiments

A numpy synthetic world (a sticky concept chain with target, draft and hashed telemetry) wired to an exact speculative decoder and five policies (vanilla, two oracles, the free-information baseline and a learned sidecar), so steering and analysis code can be checked against known ground truth on CPU; for researchers prototyping draft-steering ideas.

Use

  • Copy src/sideband/ whole: pipeline.py imports synthetic, sidecar, steering, specdec and dists, and synthetic.py imports sketch.
  • buckets.py is here to keep test_sketch_buckets.py whole; synthetic.py does not import it.
  • Run python -m pytest from this folder.

Good to know

  • Regime warning from synthetic.py's own docstring: telemetry and the target's next-token distribution are functions of the same latent concept here, so a telemetry sidecar can at best match the free-information baseline, and whether real hidden-state sketches carry more is a question this world cannot answer by construction.
  • The copied files cite the record's decision, finding and open-question ids (D-3, D-5, D-6, D-7, D-8, D-9, D-10, D-11, F-3, F-7, F-8, OQ-1, OQ-4); those read against the record's DECISIONS.md, FINDINGS.md and OPEN_QUESTIONS.md.

In the record

The record's findings index says its first arc built the verifier and this testbed and used it to fix the shapes that every later experiment inherits (docs/FINDINGS_INDEX.md, the Synthetic world arc), and two of its decisions live in pipeline.py: the free-information baseline policy (DECISIONS.md D-5: any telemetry-steering claim is compared against steering from the target's own distribution at the last verified position, which every speculative decoder computes anyway) and the isolated telemetry random stream (D-6: policies are compared at identical seeds so trajectories are paired, and telemetry draws from its own generator so a policy that reads it cannot perturb the shared draft and verify trajectory).

sideband · folder

Findings lint: no regime line and no tracked source, no finding

A stdlib-only lint that fails a FINDINGS.md whose entries lack a regime line or a source line pointing at paths git tracks; for research repositories kept by people or coding agents, wired to make lint and CI.

Use

  • Copy tools/lint_findings.py into a tools/ folder under your repository root: it finds the root from its own location and reads FINDINGS.md there. Run python tools/lint_findings.py; wire it to make lint and CI.
  • The prefixes it checks source paths under (results/, experiments/, tests/, docs/, src/, data/, tools/) are a constant at the top of the file; change them for your layout.
  • Run python -m pytest from this folder: one of the five tests reads the record's own FINDINGS.md, which is not in this folder, and fails with a file-not-found error; the other four pass on fixtures.

Good to know

  • amber carries a different, shorter tool under the same file name; this is sideband's.
  • The lint checks that cited paths exist and that git tracks them; when git cannot answer it falls back to the existence check and says so in its OK line, except under CI (the CI environment variable), where that is a failure.

In the record

The record's decision D-4 (findings carry regime and evidence, lint-enforced; its CLAUDE.md puts it as 'no regime, no finding') says every FINDINGS entry must have a regime line and a source line with existing evidence paths, and this lint is what enforces it on every make lint and CI run. METHOD.md's section on reusing the method in another repository names this file first of its three-file kit.

Landing text: generated prose whose every number traces to a payload field

A stdlib-only tool for writing the text that lands a result: pairs of generated sentences and the payload fields they quote, a check that no number in the text is unknown to a payload, a banned-phrase assertion, a line-ending normaliser and a CLI; for research repositories whose results are landed by a coding agent.

Use

  • Copy tools/landing_text.py; its Pair expects the record's payload schema (conclusion.labels, conclusion.deltas, provenance), so adapt the field names to your payloads.
  • Run python -m pytest from this folder. One test needs the record's committed R2 payloads and skips without them.

Good to know

  • This tool and the findings lint were catalogued as one registration kit together with an evidence-pin tool; the pin tool is bound to the record's own digest file and is not copied here.

In the record

The record keeps the rule that numbers in prose come only from files read in that session (its CLAUDE.md working practices and docs/METHOD.md), and docs/CONVENTIONS.md records the generated-landing practice this tool served in the later lanes: every number in a generated sentence must trace to a registered payload field, and the text refuses banned phrases before it is written.

sideband · agent

Critic lane: an adversarial reviewer agent that recomputes from state files

A Claude Code review-agent prompt and a /critic skill that check an experiment change or a finding against a nine-item checklist, tag each objection BLOCKING or ADVISORY, and in recompute mode re-derive the asserted numbers from committed state files; for researchers who run experiments with a coding agent.

Use

  • Save sideband-critic.md as .claude/agents/sideband-critic.md in your project and skills/critic/SKILL.md as .claude/skills/critic/SKILL.md; then ask Claude Code to run the critic on a diff, a finding or a payload.
  • Rewrite the nine checklist items for your domain before relying on it: as copied they cite this record's decisions, findings and a kill criterion (D-2, D-5, D-6, D-7, D-9, F-3, F-5, F-6, K-5).
  • The agent file pins model: opus and a tool allowlist (the read tools plus python and git commands; the file itself says nothing mechanical keeps its use read-only); both are settings to restate for your host.

Good to know

  • The catalogue scored this piece 3: the two files drop into any Claude Code repository's .claude/ unchanged, but the agent's 'Running inside the harness' section names the record's own harness (its plan gate, scratchpad convention and a global editable install), and the dispatch paragraphs that call it live inside harness-managed command files that are not copied.
  • METHOD.md says the critic's round reports are not committed; a recovered selection of them lives in the record's docs/audits/critic-recovered/, whose README says where the reports and the dispatch briefs lived. A workflow note for a reader outside the record (briefs, reports, verbatim saves) is still to be written before this can be a card.

In the record

The record's workflow runs this agent before any finding is committed and before experiment changes merge; its highest-value mode recomputes the asserted labels and numbers from the committed state files rather than reading the diff. METHOD.md's reuse section names it second of its three-file kit and says to rewrite the nine checklist items for your domain while keeping the shape: named leak channels, the dominated baseline, regime abuse, survivorship, pairing, the banned claim class, kill-criteria dodging, the BLOCKING and ADVISORY tags, and the closing 'What would change my mind:'.
